# 量測缺漏的時候，成本怎麼分攤

監控斷線的時候，成本並沒有跟著停：節點照跑、雲端照計費、機器照折舊。
但是你失去了「這些錢該分給誰」的依據。

這份文件講的是那段時間怎麼辦。內容是在實機上做出來、量過的，不是設計稿。

## 先把兩件事分開：總額 ≠ 分攤比例

這是整件事的關鍵，而 OpenCost 把它們算在一起，所以它一斷，兩個都沒了。

- **總成本**來自帳單、資產折舊、採購合約。Prometheus 掛掉不會讓這筆錢消失。
- **分攤比例**才是來自量測資料。

所以缺資料影響的只有比例，**總額必須原封不動**。

如果照「沒量到就不算」處理，結果是總額對不上帳單，而短收的部分會自動落到平台團隊頭上——
這其實也是一種分攤方式，只是沒有人做過這個決定，也沒有人知道它發生了。這是最糟的一種。

## 降級階梯

缺資料時往下降一階，每一階都要在明細上標記來源：

| 階 | 依據 | 適用 | 誤差 |
|---|---|---|---|
| 1 | 實際量測 `max(申請, 用量)` | 正常 | — |
| 2 | 鄰近時段的部門比例（空白前後各取一段） | 分鐘～小時級空白 | 很小，工作負載組成在短時間內很穩定 |
| 3 | **宣告量**：`replicas × requests`，資料來自 API server | Prometheus 掛了但叢集還活著 | 見下方實測 |
| 4 | 前一帳期的部門比例 | 跨日的長空白 | 中等，會錯過當期的變化 |
| 5 | 固定分攤鍵（人頭、預算比例、事先約定） | 完全無資料 | 大，但至少是講好的 |
| 6 | 掛到平台共用成本 | 確實無法歸屬 | — |

**第 3 階最值得投資，因為它的資料來源跟 Prometheus 無關。** 兩個系統同時掛的機率，
遠低於任何單一系統自己掛掉。這個 repo 的 `snapshotter/` 就是第 3 階。

## 這個 repo 實作了什麼

### 1. 覆蓋率量測（`app/app.py` 的 `coverage()`）

報表會直接問 Prometheus「這段區間到底量到了多少」，低於 99.5% 就在畫面最上方顯示，
並列出缺漏區段的起訖與長度。

- 抓取間隔是**跟 Prometheus 的 target 問出來的**，不是猜的。猜錯會讓覆蓋率系統性偏高或偏低，
  而且沒有任何徵兆——帳單上「99% 完整」如果其實是 66%，比沒有這個數字更糟。
- 問不到就退回 60 秒，而且會在畫面上註明這個數字只能參考。
- 點數上限 1500，所以比一個 step 更短的斷層抓不到。查 7 天時 step 會放大到約 6 分鐘。

實機量到的例子（2026-09-24 查最近 24 小時）：

```
覆蓋率 86.31%，缺 197 分鐘
缺漏區段：2026-09-23T05:54:00Z → 2026-09-23T09:11:00Z
```

那是筆電闔蓋移動的三個多小時。**報表在加上這個之前照樣產出，只是少算了 13.69% 的時間，
畫面上完全看不出來。** 這就是為什麼要先做這件事。

### 2. 宣告量快照（`snapshotter/`）

每 5 分鐘把每個 Running Pod 的 `requests` 與部門標籤存成一份 JSON。只讀 API server
（pods、namespaces，`get`/`list`），不碰 Prometheus，也不需要任何寫入權限。

實測每份快照 6 KiB（36 個 Pod）：5 分鐘一次是**每天 1.7 MiB**，保留 35 天約 59 MiB。
資源用量 CPU 10m、記憶體 64Mi 以下。

兩個實作細節會直接影響金額：

- **Pod 的宣告量不是「所有容器加起來」**：排程器取「一般容器總和」與「init container 峰值」
  的較大者，而原生 sidecar（`restartPolicy: Always` 的 init container）要併入總和，
  並且只有**排在 init 前面**的 sidecar 才算進那一顆的峰值。`test_snapshot.py` 有逐項驗算。
- **ServiceAccount token 要每次重讀**。現在的投射式 token 大約一小時輪替一次，
  啟動時讀一次就快取的話，這支程式會在一小時後開始收到 401——而且是在你最需要它的時候。

## 宣告量法到底準不準

沒有量過誤差的備援方案，跟沒有備援方案差不多：真的要用的時候，你不知道該不該相信它。

所以 `fallback.py` 有一個 `--compare` 模式：在**資料正常的期間**跑，把宣告量算出來的
分攤比例跟 OpenCost 的實測比一比。

```bash
python3 fallback.py --snapshots ./snapshots --last 20m --compare http://127.0.0.1:9003
```

實機量到的結果（15 分鐘、15 筆快照、每分鐘一筆；lab 叢集 36 個 Pod）：

| 部門 | 宣告量份額 | 實測份額 | 差距 |
|---|---:|---:|---:|
| 無法分攤 | 54.02% | 51.34% | +2.68 pp |
| 製造部 | 26.27% | 25.95% | +0.32 pp |
| 研發部 | 14.78% | 17.84% | **−3.06 pp** |
| 資訊部 | 4.93% | 4.87% | +0.06 pp |

**總量差 −1.23%**（宣告 3.0450 核 vs 實測 3.0829 核），**份額最大差 3.06 個百分點**。

差距集中在研發部，因為那裡的工作負載（模型訓練、建置）會超過申請量在跑；
其他部門的申請量遠大於用量，所以幾乎完全吻合。

比較的時候要注意：**OpenCost 實際涵蓋的時間常常比你要求的短**（這次要求 15 分鐘、
它回 12 分鐘），所以不能直接比總量，要各自除以自己涵蓋的時長換算成速率再比。
`fallback.py` 已經這樣處理。

**誤差的方向是固定的：宣告量法會低估「用量超過申請量」的工作負載**，因為 OpenCost 計價依
`max(申請, 用量)`，而快照只看得到申請量。所以你的叢集有多少爆量的工作負載，就決定了誤差有多大。
反過來說，申請量遠大於用量的叢集（多數企業叢集都是），這個方法會非常接近。

**要在自己的環境跑過再決定信不信它。** 上面的數字是這個 lab 的，不是你的。

## 來源標記與門檻

每一列明細都要帶 `basis`：`measured` / `interpolated` / `declared` / `prior_period` / `policy`，
帳單上顯示一行「本期 X% 的成本以推估方式分攤」。爭議來的時候可以指著看，而不是靠記憶解釋。

建議的門檻（寫在計價政策裡，不要寫死在程式裡）：

| 覆蓋率 | 處理 |
|---|---|
| ≥ 99% | 直接出帳 |
| 95–99% | 出帳，但標示推估比例與方法 |
| < 95% | **擋住結帳**，要人工核准才能放行 |

「擋住」不是不出帳，是改成需要有人簽名為那份推估負責。

## 誤差要偏哪一邊，是政策決定

推估一定有誤差。建議**推估的部分優先掛在平台共用，不要分給部門**，除非空白很短：
部門對「被多收」的敏感度遠高於平台對「多扛一點」，而一次爭議的處理成本高過那筆錢本身。

但要設上限。如果空白永遠由平台吸收，部門就沒有動機配合維持環境穩定，超過上限就要往回攤。

## 空白的成因決定走哪一階

- **監控系統自己的問題**（Prometheus OOM、磁碟滿）→ 平台的責任，推估誤差由平台吸收。
- **節點或叢集真的關機** → 先問「成本有沒有真的發生」。雲端 on-demand 可能真的沒發生；
  預留執行個體、地端折舊、授權費照樣發生，要照原比例分掉。
- **部門自己把工作負載弄壞、拿不到 metrics** → 用宣告量算，結果對該部門不利也合理。

## 最後：部分缺漏比完全缺漏危險

全部掛掉你看得出來。少數節點的 exporter 掛掉時，報表照樣產出、看起來一切正常，
只是那幾個部門被少算了，總額悄悄對不上。

所以要檢查的不是「有沒有資料」，是：

- **預期的 target 數量 vs 實際回報的數量**；
- **分攤總額 vs 帳單總額**的差異。

這跟 `examples/precheck.sh` 踩過的坑是同一個形狀：檢查 port 有沒有開，
不等於檢查回來的是不是 OpenCost。
